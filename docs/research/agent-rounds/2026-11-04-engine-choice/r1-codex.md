**가장 짧은 답:** three.js 없이도 WILD CROWN은 구현할 수 있다. 다만 대체 라이브러리를 쓰더라도 현재 장면 코드를 연결하거나 다시 써야 한다. 확인 가능한 최소 변경 범위는 `three`를 직접 import하는 8개 파일이며, 그것만으로 작업량의 하한을 시간으로 환산할 수는 없다.

| 선택지 | 이 게임의 요구를 채우는가 | 큰 대가 |
| :-- | :-- | :-- |
| **웹 1급: Babylon.js·PlayCanvas** | 가능. 체스판·기물·섬·클립 애니메이션을 표현할 수 있다. | 장면, 카메라, 효과, GLB 로딩 동작을 새 API에 맞춰 검증해야 한다. |
| **웹 1급: 순수 WebGL/WebGPU** | 가능. | 로더·애니메이션·장면 관리까지 직접 책임져야 하므로 1인 개발에 불리하다. |
| **웹 1급: Godot·Unity 웹 내보내기** | 게임 자체는 가능. | React HUD, 빌드, 배포, 브라우저 연동의 경계를 다시 설계해야 한다. |
| **네이티브 1급: Godot·Unity·Unreal** | 게임 자체는 가능. 웹을 2급으로 두거나 포기한다면 후보가 된다. | 현재 웹 제품을 사실상 새 제품으로 옮기는 결정이다. |

기존의 “three 유지 + Blender 부분 도입” 결론이 **틀릴 수 있는 첫째 경우**는 웹 성능 병목이 장면 구성 개선 뒤에도 남는 것이다. 조기 신호는 같은 기기·해상도·장면에서 드로우콜과 프레임 시간을 줄인 뒤에도 목표에 못 미치는 결과다. 둘째는 추가 룩이 늘면서 GLB별 리그·클립·머티리얼 검수가 반복적인 수작업이 되는 경우다. 셋째는 스토어 제품에 필요한 기기 기능이나 배포 방식이 웹 기반 경로와 맞지 않는 경우다. 각각 렌더러, 제작 파이프라인, 제품 형태의 문제이므로 해결책도 같지 않다.

반대로 **지금 Godot로 옮겨 후회할 세 경우**도 있다. 웹 초대 대전과 상점 출시가 이전 작업 때문에 늦어지는 경우, GLB 125개의 외형과 애니메이션이 가져오기 과정에서 달라져 검수량이 커지는 경우, 기존 React·TypeScript·`chess.js` 작업 흐름을 잃고 한 사람이 게임 로직과 UI를 함께 재구축해야 하는 경우다. `chess.js`의 규칙과 테스트 사례는 설계 자산으로 가져갈 수 있지만, Godot에서 현재 JS 호출 코드를 그대로 쓸 수 있다고 가정해서는 안 된다.

**하이브리드는 성립한다.** Babylon.js 또는 PlayCanvas로 렌더만 바꾸고 React·Vite·`chess.js`·GLB 제작 도구는 유지할 수 있다. 다만 `GLTFLoader`, 스켈레톤 복제, 윤곽선, 카메라 조작, 메시 병합과 클립 재생이 새 엔진에서도 같은 결과를 낸다는 보장은 없다. 특히 6,300줄짜리 장면 파일의 렌더 코드와 게임 진행 코드가 얼마나 섞였는지 확인하기 전에는 “렌더만 교체”의 범위를 확정할 수 없다.

**이전 비용은 추정이다.** 하이브리드 평가의 작업량을 가늠하려면 8개 import 파일을 확인하고, 6,300줄 장면 파일에서 렌더 관련 부분을 표시한 뒤, GLB **125개**와 테스트 **135개** 중 재검증 대상을 세어야 한다. 예컨대 장면 파일의 20~50%가 교체 대상이라고 *가정*하면 **1,260~3,150줄**이다. 이는 실제 결합도를 재지 않은 계산이며 일정 견적이 아니다. Python 에셋 도구와 GLB 원본은 가져갈 후보지만, 새 엔진의 import 결과·리그·클립은 별도 확인이 필요하다. 2~3년 손익에서 핵심 비용은 라이선스 숫자보다 이 검증 및 업그레이드 노동일 수 있다. 후보별 현행 수수료와 LLM 협업 생산성은 확인 못 했다. LLM이 현재 웹 스택을 더 쉽게 다룰 것이라는 판단 역시 **인상**이다.

**결론은 조건부다.** 동일한 대표 장면에서 장면 최적화 후에도 목표 프레임 시간을 못 맞추고, 대체 렌더러의 시제품이 같은 화질·기능에서 안정적으로 목표를 맞춘다면 **웹 스택을 보존하는 하이브리드 이전**을 선택한다. 그것이 거짓이고 웹 배포가 계속 1급이라면 **three에 남는다**. 네이티브 전용 요구가 웹 출시보다 우선한다는 제품 결정이 확인되면 그때 Godot·Unity 네이티브 이전을 비교한다. 측정은 동일 기기에서 체스판과 섬의 대표 상태를 각각 여러 번 실행해 프레임 시간·드로우콜·화질·기능 누락을 기록하고, GLB 몇 개로 로딩·리그·클립 시제품을 만드는 방식이다. 소요 시간은 재 보지 않았다.

**틀릴 수 있는 곳 세 가지:** 장면 파일의 실제 렌더 결합도, 대체 엔진의 동일 장면 성능, 스토어 출시에서 웹 기반 방식의 적합성이다. 또한 §3의 “멀티플레이가 핵심이면 엔진 재검토”는 다시 따져볼 만하다. 현재의 Supabase Realtime 구상에서 멀티플레이 자체가 렌더러 교체 이유인지는, 네트워크 상태와 장면 코드의 결합을 확인해야 판단할 수 있다.
