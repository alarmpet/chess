## 1. [C] 독립 설계안

### 1.1 구조: 모듈·경계·데이터 흐름

- **규칙 상태 한 곳:** `chess.js`가 차례, 합법수, 승급, 종료 판정을 소유한다. 화면의 기물 객체는 규칙 상태를 표시하는 투영이다.
- **수 실행 절차:** 입력 또는 AI의 수 제안 → 규칙 엔진에서 검증·확정 → 이동 결과를 안무에 전달 → 안무 완료 후 다음 입력 허용. 애니메이션이 끝날 때까지 규칙 확정을 미루는 현재 방식은 교체한다.
- **기물 어댑터:** 팩 매니페스트의 역할(`move`, `attack`, `hit`)을 실제 클립 이름과 효과에 연결한다. 리그 종류만으로 클립을 추측하지 않는다.
- **렌더러와 로더:** 기존 WebGL 장면을 유지하면서 팩 로더를 별도로 둔다. 로더는 팩 파일·확장 기능·오류를 처리하고, 장면은 로딩 결과만 받는다.
- **AI 워커:** 현재 국면과 요청 번호를 워커에 보낸다. 돌아온 수는 요청 번호와 현재 국면이 일치할 때만 적용한다. 재시작·되돌리기 후의 늦은 응답을 버릴 수 있어야 한다.
- **이전 순서:** 규칙 상태와 화면 상태의 경계를 먼저 만들고, 클립 어댑터와 팩 로더를 붙인다. 이후 AI와 장면 효과를 옮긴다.

### 1.2 왜 이 구조인가

현재 `executeChessMove`는 이동을 시작하고, `finishMove`에서야 `boardState`와 차례를 바꾼다(`wizardChessEngine.js:2072–2075, 2477–2523`). 이 결합을 끊어야 규칙 교체, AI 워커, 리플레이가 같은 수를 안정적으로 참조한다. 현재 기물 재생은 이름의 부분 문자열을 찾으므로(`:1591–1598`) 동물 팩의 `Walk` 같은 이름을 역할 매핑으로 전달해야 한다. 4,969행 파일은 기능별 경계를 먼저 만든 뒤 옮기는 편이 §4.1의 단계별 이전 원칙에도 맞다. WebGL 유지와 기존 장면의 단계별 검증은 GLSL 변경 위험을 한 번에 떠안지 않게 한다. 주당 15~20시간 제약에서는 사자 한 종을 실제 판 위에서 움직이고 잡게 하는 경로를 우선 검증할 수 있다.

### 1.3 이 설계가 틀릴 수 있는 곳 셋

1. **규칙 확정 시점:** 수를 먼저 확정하면 현재 HUD·되돌리기·멀티플레이가 애니메이션 도중 다음 차례를 보여줄 수 있다. 일반 이동·잡기·캐슬링·승급 각각에서 입력 직후, 접촉 시점, 안무 종료 시점의 규칙 상태와 화면 상태를 기록해 확인한다.
2. **클립 어댑터:** 매니페스트 이름 매핑만으로는 발이 미끄러지거나 접촉이 빗나갈 수 있다. 사자 한 종의 `Walk`와 `Attack`을 재생하고 클립 시간, 접촉 이벤트 시간, 공격자와 피격자의 월드 좌표를 프레임별로 기록한다.
3. **성능 예산:** 머티리얼 공유만으로 드로우콜 40 이하가 되지 않을 수 있다. 32개 기물과 바이옴을 얹은 실제 잡기 장면에서 `renderer.info.render.calls`, 프레임 시간 p95, 텍스처 메모리를 각각 측정한다.

### 1.4 하지 않을 것과 이유

Phase 0에서 WebGPU 전환이나 장면 전체 재작성을 하지 않는다. 기존 코드에 `ShaderMaterial`과 `onBeforeCompile` 수정이 있다(`:561, :700, :1010`). 또한 옛 규칙 엔진을 새 엔진과 영구 병행하지 않는다. 두 규칙 상태가 각각 수를 확정하면 불일치의 원인이 된다.

### 1.5 가장 약한 결정

**규칙을 안무 전에 확정하는 순서**다. 엔진 분리는 쉬워지지만 현재 멀티플레이·되돌리기의 타이밍을 함께 바꿔야 한다. 위 세 시점 기록으로 먼저 확인해야 한다.

## 3. [C]에서 찾은 문제

[문제 1] 접촉 시각을 비율로 기록하면 공격이 어긋난다  
어디    기획서 §1.1, §3.1, §5.1; `wizardChessEngine.js:2437–2444, 2598–2626`  
무엇을  “값이 클립 길이 대비 **비율**(`contactClip: 0.56~0.60`)”  
왜 문제 클립 시간이 2초인 경우 비율 0.56은 1.12초를 뜻하지만, 현재 엔진은 `tApproach + 0.56 / timeScale`에 접촉시킨다. 렌더에서 잰 비율을 그대로 넣으면 피격 반응과 이펙트가 실제 발·머리 접촉보다 빨라진다.  
고치는 법 `contactClip`·`blowClip`의 단위를 **클립 시간(초)**으로 명시하고 측정값을 초로 변환한다. 비율을 쓰려면 소비 코드가 클립 길이를 곱하도록 함께 바꾼다.  
확신도  높음

[문제 2] 기존 클립 검색으로는 동물 팩의 이동·피격 모션이 재생되지 않는다  
어디    기획서 §4.3, §9 Phase 1; `wizardChessEngine.js:1591–1598, 2161, 2649`  
무엇을  “`playPieceClip(piece, 'Move', true, 0.10);`”  
왜 문제 현재 재생기는 요청 문자열이 실제 클립 이름에 포함돼야 동작한다. 기획서의 동물 클립 이름은 `Walk`, `Idle_HitReact_Left` 등이다(기획서 §4.3). `Move`와 `Shatter` 요청은 이 이름들에 매치되지 않아 이동하거나 피격될 때 해당 클립이 빠진다.  
고치는 법 Phase 1 인게임 검증 전에 역할→클립 이름 어댑터를 연결하고, 없는 역할의 대체 동작을 정한다.  
확신도  높음

[문제 3] 현재 머티리얼 교체 경로를 재사용하면 동물 텍스처가 사라진다  
어디    기획서 §4.3, §5.1; `wizardChessEngine.js:1518–1534`

왜 문제 현재 `instantiatePiece`는 대부분의 메시 재질을 백·흑 단색 재질로 바꾼다. 새 동물 GLB를 이 경로에 연결하면 제작한 색과 표면 텍스처를 표시하지 못한다.  
고치는 법 클래식 석상 팩의 재질 교체를 그 팩에 한정하고, 동물 팩은 원본 재질을 유지한 채 진영 색을 별도 장식·효과로 적용한다.  
확신도  높음

## 4. [C] 자료에서만 드러나는 것

- `contactClip`, `blowClip`, `swingStartClip`은 이름에 `Clip`이 들어가지만 **길이 대비 비율이 아니라 클립 시간값**이다(`wizardChessEngine.js:2437–2444, 2598–2626`).
- 흑 기물은 별도 모델이 아니라 백 모델 템플릿을 공유하고, 인스턴스에서 재질을 바꾼다(`:1411–1416, 1517–1534`). 새 팩 로더 설계에 직접 영향을 준다.
- 현재 판의 규칙 상태와 안무 상태가 한 함수 안에 있다. `finishMove`에서 판 갱신·승급·차례 변경을 함께 한다(`:2477–2523`).
- 현재 자동 테스트는 규칙이나 안무의 정합성을 검사하지 않는다(`applet.test.mjs:9–74`). 다만 엔진은 `window.wizardChess.stepBy`라는 수동 프레임 진행 수단을 이미 제공한다(`wizardChessEngine.js:4699–4705`).
- 왕의 기존 체크메이트 연출은 `Death` 클립이 아니라 메시 전체를 기울이는 자세 계산이다(`:3573–3591`). 왕관 계승 안무는 기존 전도를 단순히 이름만 바꾸는 작업보다 크다.
