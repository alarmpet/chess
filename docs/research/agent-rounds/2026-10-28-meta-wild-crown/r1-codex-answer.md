## 1. [C] 게임 디자인·경제 설계안

**진행 축을 분리한다.** 랭크 레이팅은 표준 체스 대전 결과로 실력을 나타내고 매칭에 쓴다. XP·레벨은 플레이 이력과 꾸미기 해금에 쓴다. 상점의 C/B/A/S는 **기물의 외형 등급**으로 표시하며, 플레이어 레이팅과 다른 이름·화면 영역에 둔다. 상품명도 “A급 비숍”보다 “A등급 비숍 외형”으로 쓰고, 이동 규칙이 같음을 구매 화면에 명시한다. 레이팅 산식, XP량과 레벨 곡선은 재 보지 않았다.

| 코인 흐름 | 설계 | 남용·인플레 제어 |
| :--- | :--- | :--- |
| 획득: 온라인 대전 완료 | 승·무·패 모두 완료 보상. 승리 추가 보상은 검증된 결과에만 적용 | 서버가 확정한 결과만 반영. 중도 포기와 반복 상대 보상 규칙 필요 |
| 획득: 미션 | 공개된 조건을 달성하면 지급 | 동일 이벤트 중복 지급 방지. AI·로컬 대전은 소비 가능한 코인의 원천에서 제외 |
| 소비: 지정 상품 구매 | 원하는 외형·장비를 확정 가격으로 직접 구매 | 구매와 잔액 차감을 한 거래로 기록 |
| 소비: 꾸미기 변경 | 팔레트·이펙트 등 공개된 선택지를 직접 구매 | 판매 목록과 코인 유입량을 함께 조정. 확률 구매는 두지 않음 |

정확한 지급량, 가격, 미션 주기, 반복 대전 제한은 **재 보지 않았다**. 출시 전 실제 플레이 시간과 구매 도달 시간을 재고 정해야 한다. 무료 기본 외형은 완성된 품질로 제공한다.

**외형 등급은 완성도와 연출 범위의 약속이다.** C는 기본 캐릭터와 색상, B는 장식·재질 변형, A는 눈에 띄는 모델 장식과 고유 공격 효과, S는 고유 등장·승리 연출까지 포함한다. 어느 등급도 이동, 시야, 피격 판정, 수 계산, 애니메이션 접촉 시각을 바꾸지 않는다. 체스판 가독성과 성능 게이트는 모든 등급에 동일하게 적용한다.

[팩 매니페스트](/D:/chess/docs/PLAN.md:127)의 기물 정의에 `variants`를 추가해 상품별 `id`, `tier`, `model`, `keepMaterials`, `vfx`, `sfx`, `equipSlots`를 둔다. 리그별 `sockets`에는 `head`·`back` 같은 의미상 위치와 실제 본 이름 또는 GLB 앵커 이름을 매핑한다. 착용 장비는 해당 본·앵커 아래에 붙여 모션을 따라가게 한다. 본이 없는 사진 기반 캐릭터에는 제작 시 앵커를 넣고, 매핑이 없으면 매니페스트 검증에서 거부한다. 소유·착용 상태는 팩 파일과 분리해 계정의 상품 ID와 슬롯별 선택으로 저장한다. 비숍 외형 한 건을 사면 해당 진영의 비숍 역할에 적용되도록 판매 단위를 명확히 한다.

[현재 기물 생성 코드](/D:/chess/src/wizardChessEngine.js:1518)는 메시 재질을 교체한다. 동물 외형에는 기획된 `keepMaterials` 경로가 선행돼야 등급별 재질이 살아남는다. 왕관 장비는 킹의 본·앵커를 따라가야 한다. [현재 킹 전도](/D:/chess/src/wizardChessEngine.js:3593)는 메시 자세를 기울이므로, 왕관 계승 장면에서 장비의 부착과 분리 연출을 별도로 설계해야 한다.

**능력 기물은 추후 별도 캐주얼 규칙으로만 시험한다.** 그 경우 `standard` 규칙 상태와 `variant` 규칙 상태를 게임 시작 때 확정하고, 수 검증·승패 판정·기록 형식을 분리한다. `variant`를 chess.js·Stockfish에 그대로 넘기지 않는다. 별도 엔진과 회귀 사례가 갖춰지기 전에는 온라인 랭크와 코인 보상에 연결하지 않는다.

보상 루프는 *대전 완료 → 결과 확정 → 레이팅 또는 XP·코인 반영 → 공개된 상품 선택 → 착용 → 다음 대전*이다. 뽑기나 중복 카드가 없어도 목표 상품을 정하고 모으는 재미를 준다. 클라이언트의 로컬 결과만으로 구매 가능한 코인을 지급하지 않는다.

**로드맵 제안** — 추가 주수는 개발 실측이 아닌 편성안이며 재 보지 않았다.

| Phase | 메타게임 작업 |
| :--- | :--- |
| 0a·0b, 각 기존 1주 | 규칙 결과와 화면 연출을 분리할 때 `matchResult` 계약을 둔다. 표준 규칙 결과만 랭크 대상으로 지정한다. |
| 1, 기존 3~4일 | 사자 1종에 장비 앵커·재질·효과가 카메라 거리에서 읽히는지 확인한다. |
| 2·3, 기존 2~3주·3주 | 두 왕국 팩에 공통 소켓·등급 외형 제작 규격과 검증을 적용한다. |
| 4, 기존 3주 **+ 제안 1주** | 스킨 공방과 함께 소유·착용·상점 미리보기 UI를 만든다. |
| 5, 기존 2주 **+ 제안 2주** | 온라인 결과를 전제로 레이팅·XP·코인 원장·확정 구매를 붙이고 남용 테스트를 한다. |
| 6, 이후 | WebGPU와 별개로 능력 기물은 별도 검토한다. |

이 편성의 총 기간은 기획서의 **12~13주에서 제안상 15~16주**로 늘어난다. 온라인 결과를 신뢰할 수 있는 기술 경로가 Phase 5의 선행 조건이다.

**틀릴 수 있는 곳 셋:** 등급별 연출이 체스판을 산만하게 만들 수 있다. 영구 소장품만 파는 상점은 코인 소비가 늦어져 잔액이 쌓일 수 있다. Phase 5에 온라인 대전과 경제를 함께 넣는 일정은 1인 개발에서 부족할 수 있다. **하지 않을 것:** 랭크용 능력치 판매, 확률 상품, 로컬 기록을 온라인 코인으로 전환, 등급별 체스 규칙 변경. **가장 약한 결정:** 코인 경제의 지급·가격·소비 균형이다. 이용 데이터가 없어 아직 수치로 확정할 근거가 없다.

고치는 법: 랭크 상품은 외형으로 한정하고 능력 기물은 별도 캐주얼 규칙 엔진 이후로 옮긴다.

## 3. 통합자 가정 판정

**유지.** 랭크는 외형만 바꾼다. §4.5의 chess.js·Stockfish 계획은 표준 체스에 맞춰져 있다. 능력 기물을 랭크에 넣으면 합법 수, AI, 리플레이, 회귀 테스트와 공정성 판단을 새로 만들어야 한다. 캐주얼 변형 규칙은 별도 엔진이 준비된 뒤 검토하는 편이 맞다.

## 4. 내 자료에서만 드러나는 것

[App.tsx](/D:/chess/src/App.tsx:81)의 현재 HUD는 대전 로비·상점·장비 화면 구조가 아니라 AI 수 두기·진영 전환·초기화 중심이다. 따라서 메타게임은 버튼 몇 개 추가하는 작업이 아니라 모드별 조작과 별도 화면 흐름이 필요하다. 또한 [흑백 템플릿 공유](/D:/chess/src/wizardChessEngine.js:1411)와 [인스턴스 재질 교체](/D:/chess/src/wizardChessEngine.js:1518) 때문에 진영별 외형 검증이 중요하다. [킹 전도 코드](/D:/chess/src/wizardChessEngine.js:3593)는 왕관 착용·계승을 자동으로 해결하지 않는다.

## 5. 우선순위 셋

1. **랭크 공정성:** 능력·AI 조작·로컬 결과 보상을 배제하고, 확정 결과에만 레이팅과 코인을 연결한다.
2. **실제로 보이는 상품:** 재질 보존, 리그 소켓, 착용 상태와 체스판 가독성을 먼저 검증한다.
3. **지속 가능한 보상:** XP와 레이팅을 분리하고, 코인 가격·지급량은 플레이 실측 후 정한다.

[현재 기물 생성 코드](/D:/chess/src/wizardChessEngine.js:1518)는 메시 재질을 교체한다. 동물 외형에는 기획된 `keepMaterials` 경로가 선행돼야 등급별 재질이 살아남는다. 왕관 장비는 킹의 본·앵커를 따라가야 한다. [현재 킹 전도](/D:/chess/src/wizardChessEngine.js:3593)는 메시 자세를 기울이므로, 왕관 계승 장면에서 장비의 부착과 분리 연출을 별도로 설계해야 한다.

**능력 기물은 추후 별도 캐주얼 규칙으로만 시험한다.** 그 경우 `standard` 규칙 상태와 `variant` 규칙 상태를 게임 시작 때 확정하고, 수 검증·승패 판정·기록 형식을 분리한다. `variant`를 chess.js·Stockfish에 그대로 넘기지 않는다. 별도 엔진과 회귀 사례가 갖춰지기 전에는 온라인 랭크와 코인 보상에 연결하지 않는다.

보상 루프는 *대전 완료 → 결과 확정 → 레이팅 또는 XP·코인 반영 → 공개된 상품 선택 → 착용 → 다음 대전*이다. 뽑기나 중복 카드가 없어도 목표 상품을 정하고 모으는 재미를 준다. 클라이언트의 로컬 결과만으로 구매 가능한 코인을 지급하지 않는다.

**로드맵 제안** — 추가 주수는 개발 실측이 아닌 편성안이며 재 보지 않았다.

| Phase | 메타게임 작업 |
| :--- | :--- |
| 0a·0b, 각 기존 1주 | 규칙 결과와 화면 연출을 분리할 때 `matchResult` 계약을 둔다. 표준 규칙 결과만 랭크 대상으로 지정한다. |
| 1, 기존 3~4일 | 사자 1종에 장비 앵커·재질·효과가 카메라 거리에서 읽히는지 확인한다. |
| 2·3, 기존 2~3주·3주 | 두 왕국 팩에 공통 소켓·등급 외형 제작 규격과 검증을 적용한다. |
| 4, 기존 3주 **+ 제안 1주** | 스킨 공방과 함께 소유·착용·상점 미리보기 UI를 만든다. |
| 5, 기존 2주 **+ 제안 2주** | 온라인 결과를 전제로 레이팅·XP·코인 원장·확정 구매를 붙이고 남용 테스트를 한다. |
| 6, 이후 | WebGPU와 별개로 능력 기물은 별도 검토한다. |

이 편성의 총 기간은 기획서의 **12~13주에서 제안상 15~16주**로 늘어난다. 온라인 결과를 신뢰할 수 있는 기술 경로가 Phase 5의 선행 조건이다.

**틀릴 수 있는 곳 셋:** 등급별 연출이 체스판을 산만하게 만들 수 있다. 영구 소장품만 파는 상점은 코인 소비가 늦어져 잔액이 쌓일 수 있다. Phase 5에 온라인 대전과 경제를 함께 넣는 일정은 1인 개발에서 부족할 수 있다. **하지 않을 것:** 랭크용 능력치 판매, 확률 상품, 로컬 기록을 온라인 코인으로 전환, 등급별 체스 규칙 변경. **가장 약한 결정:** 코인 경제의 지급·가격·소비 균형이다. 이용 데이터가 없어 아직 수치로 확정할 근거가 없다.

## 3. 통합자 가정 판정

**유지.** 랭크는 외형만 바꾼다. §4.5의 chess.js·Stockfish 계획은 표준 체스에 맞춰져 있다. 능력 기물을 랭크에 넣으면 합법 수, AI, 리플레이, 회귀 테스트와 공정성 판단을 새로 만들어야 한다. 캐주얼 변형 규칙은 별도 엔진이 준비된 뒤 검토하는 편이 맞다.

## 4. 내 자료에서만 드러나는 것

[App.tsx](/D:/chess/src/App.tsx:81)의 현재 HUD는 대전 로비·상점·장비 화면 구조가 아니라 AI 수 두기·진영 전환·초기화 중심이다. 따라서 메타게임은 버튼 몇 개 추가하는 작업이 아니라 모드별 조작과 별도 화면 흐름이 필요하다. 또한 [흑백 템플릿 공유](/D:/chess/src/wizardChessEngine.js:1411)와 [인스턴스 재질 교체](/D:/chess/src/wizardChessEngine.js:1518) 때문에 진영별 외형 검증이 중요하다. [킹 전도 코드](/D:/chess/src/wizardChessEngine.js:3593)는 왕관 착용·계승을 자동으로 해결하지 않는다.

## 5. 우선순위 셋

1. **랭크 공정성:** 능력·AI 조작·로컬 결과 보상을 배제하고, 확정 결과에만 레이팅과 코인을 연결한다.
2. **실제로 보이는 상품:** 재질 보존, 리그 소켓, 착용 상태와 체스판 가독성을 먼저 검증한다.
3. **지속 가능한 보상:** XP와 레이팅을 분리하고, 코인 가격·지급량은 플레이 실측 후 정한다.
